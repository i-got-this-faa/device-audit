# Direct-UDP lab evidence, 2026-10-16

This is an observed same-host Linux lab, not production mesh or a two-machine
LAN, WAN, NAT, DERP-only, or Windows runtime qualification.

Base: device-audit `origin/main` at `fcf1329`. Tailcat:
`52fbad323e9d352f1febb623e0975368e9a8cbdd`. Toolchain:
`go version go1.27.1-X:nodwarf5 linux/amd64`. Network access and module downloads
succeeded without dependency replacements or upstream modifications.

## Observed traced run

Command: `networking/tailcat-lab/run-proof.sh --trace`.
The command exited 0. Trace payloads and raw socket addresses are not retained.
Each phase starts new server and client OS processes. Phase 1 reloads phase 0's
network key files and restarts the same bootstrap address. The TLS relay process
runs inside the parent test runner.

| Observation | Initial start, phase 0 | Restart, phase 1 |

The first connection is a one-round-trip warmup. The second connection starts
only after both the relay listener and existing DERP connections close, and the
relay TCP port is checked unreachable. All eight fresh 32-byte random challenges
receive the expected SHA-256 response. Server `PeerKey` equals the allowed network
key on each accepted flow. Both server snapshots report a direct path, and the
client's direct endpoint is a local host-interface address.

These fingerprints refer to temporary random lab identities. No private keys,
PSKs, full bootstrap addresses, device IDs, or raw logs are committed.

The same traced run observed **132 successful UDP send syscalls and 91 successful
UDP receive syscalls** across the peer experiment. These are syscall counts,
including discovery and negative tests, not packet counts or a benchmark.
The relay-off round trips plus upstream path status establish the direct
application path; socket counts independently show real host UDP activity.

On a fresh server, an unknown client with the real bootstrap secret failed
discovery and application dialing in 4001.911 ms. The server had zero peers and
zero accepted application connections. An allowlisted client with a wrong PSK
passed discovery but failed application dialing in 2008.310 ms. The server had
one discovered peer and zero accepted application connections. Timeout durations
are lab test bounds, not a production rejection-latency guarantee.

## Checks and limits

- Dedicated module vet, race tests, and `go mod verify` passed. The race run
  completed the real two-process restart and refusal proof in 20.584 seconds.
  The helper-only entry point skips in the parent and executes in child processes.

- Root `make PYTHON=.venv/bin/python check cross-build` passed: Go vet, race
  tests, formatting, all 22 Python tests, and endpoint cross-builds for Windows
  amd64 and Darwin arm64. Neither cross-build is runtime evidence.
- The first default-Python `make check` failed two malformed-timestamp vectors
  because system Python lacked `rfc3339-validator`. The documented pinned
  `models/test-requirements.txt` environment fixed this without source changes.
- Dedicated state tests reject missing, malformed, zero-key, missing-PSK,
  unknown-version, trailing-data, unknown-field, public-permission, symlinked,
  and oversized state. Explicit initialization cannot overwrite an identity.
- The configuration test rejects an empty admission key, wrong server pin,
  missing PSK, and absent/default/remote relay configurations.
- The [recovery edge case and untested flows](../README.md#limits-and-observed-recovery-edge-case)
  remain limits of this proof. They are not resolved by a successful clean run.
