# Self-hosted DERP evidence, 2026-10-21

NET04 [#84](https://github.com/i-got-this-faa/device-audit/issues/84), based on
`origin/main` at `1b56d1a`. Dependency #20 is already merged, including commit
`9cd99a1`; no changes were taken from or made to its separate owner worktree.
This is real same-host Linux runtime evidence, not production qualification.

## Reproduce and identify the runtime

```sh
make derp-lab-proof
make tailcat-lab-check
make PYTHON=.venv/bin/python check cross-build
```

Create that environment and install the pinned test dependencies before running
the checks:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r models/test-requirements.txt
```

See the [operational guide](../../../infra/networking/derp-lab.md) for namespace
prerequisites, ports, certificate requirements, and limits.

Observed tools were Go `go1.27.1-X:nodwarf5 linux/amd64`, Python 3.14.8,
nftables 1.1.7, and util-linux 2.42.4. Tailcat and DERP use the unchanged nested
module pins `52fbad323e9d` and `a0e471a35b8f`. The host Docker API was unavailable
because `/var/run/docker.sock` did not exist. The legitimate alternative,
unprivileged `unshare --user --map-root-user --net`, allowed a private loopback
interface and namespace-local nftables. No host routes, rules, containers,
Tailscale daemon, or other worktrees were altered.

An initial live run failed the namespace guard because inspecting
`/proc/1/ns/net` from the new user namespace was unavailable. The runner now
captures its actual parent network namespace before `unshare`, checks that the
child differs before configuring networking, and passes that same parent
identifier for the experiment's independent comparison. It does not weaken the
guard or change host authority. The corrected live experiment passed twice.
The final run below completed in 7.24 seconds with exit 0.

## Forced path and actual forwarding

The fresh namespace had only loopback, no route to public relays, one explicit
loopback DERP region, and no STUN service. Before either peer started:

```nft
table inet device_audit_derp {
    chain output {
        type filter hook output priority filter; policy accept;
        meta l4proto udp counter packets 12 bytes 1944 drop
    }
}
```

The counter shown is the final observed value, not the initial configuration.
The experiment parsed the live nft JSON and required the expected output hook,
UDP match, counter, and drop action, and a positive counter after discovery.
Twelve attempted UDP packets, 1,944 bytes, were dropped. Client `DiscoPing`
reported DERP region 1 with no direct endpoint. Server peer status had empty
`CurAddr` and a nonempty relay. Server `PeerKey` matched the admitted key before
any challenge reply. The real relay used TLS TCP port 40659 on loopback and
restarted on that same port with its DERP node identity preserved.

Upstream DERP protocol counters, not TLS byte estimates:

| Counter | Baseline application interval delta | Restarted relay interval delta |
| --- | ---: | ---: |
| Packets received | 15 | 12 |
| Packets sent | 15 | 10 |
| Received non-Disco packets, upstream `other` | 15 | 8 |
| Received Disco packets | 0 | 4 |
| Bytes received | 1,872 | 1,418 |
| Bytes sent | 1,872 | 1,198 |
| DERP-to-DERP mesh forwarded in/out | 0 / 0 | 0 / 0 |

The initial relay totals also included 5 Disco packets before baseline exchange.
`packets_forwarded_in/out` refer to inter-relay meshing in this upstream version;
zero is expected for a single relay and is not evidence against local client
relay traffic. Verified challenge responses, blocked UDP, path status, and
increasing received/sent non-Disco protocol counters jointly establish the path.
The intervals can include transport handshake/ACK traffic, not only payloads.

## Application attempts and relay-only restart

Both peer processes stayed alive. Client PID was 519367; server PID was 519359.
Only the DERP service listener and its active hijacked sockets were closed and
recreated. The peer processes and existing application TCP connection were not
restarted. `Accepted` stayed at one. A TCP connection to the relay port was
refused while down. Three fresh baseline challenges were validated, then a
fourth challenge was written while the relay was down.

Times are milliseconds from the client process start:

| Sequence | Start | Observation time | Observed outcome |
| --- | ---: | ---: | --- |
| 1 | 3109.809 | 3110.143 | Validated reply |
| 2 | 3110.143 | 3110.408 | Validated reply |
| 3 | 3110.409 | 3110.890 | Validated reply |
| 4 | 3111.375 | 3911.575 | Write accepted locally; 800.200 ms read timeout, no reply observed |
| 4, same pending request | 3111.375 | 7220.509 | Validated reply after relay restart on the original connection |

While the relay was down, server receipt sequences remained `[1,2,3]` and reply
count remained 3. After recovery they were `[1,2,3,4]` and 4. The outage request
was not resubmitted as a new sequence. It eventually delivered through the
existing reliable stream, so the timed-out observation is **not permanent
application loss**. This run had one deadline miss, zero observed permanent
losses among four challenges, and no recovery redial. It is not a packet-loss
rate or sustained-load measurement. No application attempts were scheduled
between the outage probe and the recovery check; the gap includes that observer
schedule and cannot establish a minimum outage or zero-loss guarantee.

| Measurement | Observed ms |
| --- | ---: |
| Relay service down, shutdown completed to new TLS listener ready | 2005.994 |
| New listener ready to successful DERP DiscoPing observation | 2103.073221 |
| Last baseline validated reply to first recovered validated reply | 4109.619350 |
| Outage challenge start to eventual reply | 4109.134 |

The relay reconnect value is time to an observed successful probe, not an exact
internal socket reconnect timestamp. The delivery gap is measured between
client reply validations. The relay-down timer starts after shutdown finishes,
so it excludes the small shutdown operation itself. Absolute validation
observations were 1792573263438124857 ns Unix for sequence 3 and
1792573267547744207 ns Unix for sequence 4. Client and parent share the host
clock; this is not a distributed-clock experiment.

At completion both peer processes were explicitly stopped, waited, and reported
exit status 0. The namespace and temporary executable were then removed.

## Checks and remaining limits

- Final `make derp-lab-proof` passed with actual outage/recovery evidence above.
- `make tailcat-lab-check` passed Go vet, race tests including the existing real
  direct/restart/admission experiment, module checksum verification, and format
  check. Final race test duration was 20.571 seconds. The explicit DERP lab skips
  in ordinary module tests and runs through its separate isolation target.
- Root `make check` passed vet, race tests, all 29 Python tests, and formatting.
- `make cross-build` passed Windows amd64 and Darwin arm64 endpoint builds.
  These are compile checks, not runtime qualification for either platform.
- Trusted TLS, public deployment, real Windows endpoints, WAN/NAT, direct-to-relay
  transition, multi-region failover, production enrollment/revocation, long
  outages, and sustained-load loss remain untested. Production mesh constructors
  still return `ErrNotImplemented`. No device-evidence signatures or chain
  commitments are created or verified here.
